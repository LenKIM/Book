# 순진한 트리

댓글을 달고, 답글을 달 수 있는 그래서 가지를 뻗어 깊게 확장하는 글 타래를 형성할 수 있다.

이런 답글 타래를 추적하기 위해, 각 답글은 답글을 다는 대상 글에 대한 참조를 가지도록 하는 단순한 해법을 선택

```sql
CREATE TABLE Comments (
  comment_id   SERIAL PRIMARY KEY,
  parent_id    BIGINT UNSIGNED,
  comment      TEXT NOT NULL,
  FOREIGN KEY (parent_id) REFERENCES Comments(comment_id)
);

```

## 목표: 계층구조 저장 및 조회하기

데이터가 재귀적 관계를 가지는 것은 흔한일. 데이터는 트리나 계층적 구조가 될 수 있다.트리 데이터 구조에서 각 항목은 노드라 불리며, 노드는 여러 개의 자식을 가질 수 있고 부모를 하나 가진다. 


### 그래서 안티패턴이 뭘까?

바로 parent_id 칼럼 추가하는 것

이 칼럼은 같은 테이블 안의 다른 글을 참조하며, 이 관계를 강제하기 위해 FK 제약 조건을 걸 수 있다.

```sql
create table Bugs
(
    bug_id     int not null,
    account_id int not null
);

create table Accounts
(
    account_id int not null
);

CREATE TABLE Comments (
  comment_id   SERIAL PRIMARY KEY,
  parent_id    BIGINT UNSIGNED,
  bug_id       BIGINT UNSIGNED NOT NULL,
  author       BIGINT UNSIGNED NOT NULL,
  comment_date DATETIME NOT NULL,
  comment      TEXT NOT NULL,
  FOREIGN KEY (parent_id) REFERENCES Comments(comment_id),
  FOREIGN KEY (bug_id) REFERENCES Bugs(bug_id),
  FOREIGN KEY (author) REFERENCES Accounts(account_id)
);
```

인접 목록에서 트리 조회

이 때 우리는 다음과 쿼리를 사용

```sql
SELECT c1.*, c2.*
FROM Comments c1 LEFT OUTER JOIN Comments c2
  ON c2.parent_id = c1.comment_id;
```

이 쿼리는 단지 트리의 두 단계만 조회. 트리의 특징 중 하나가 어느 깊이까지든 확장될 수 있다는 것이므로, 단계에 상관없이 후손들을 조회할 수 있어야 한다.

```sql
SELECT c1.*, c2.*, c3.*, c4.*
FROM Comments c1                     -- 1st level
  LEFT OUTER JOIN Comments c2
    ON c2.parent_id = c1.comment_id  -- 2nd level
  LEFT OUTER JOIN Comments c3
    ON c3.parent_id = c2.comment_id  -- 3rd level
  LEFT OUTER JOIN Comments c4
    ON c4.parent_id = c3.comment_id; -- 4th level
```

### 안티패턴 사용이 합당한 경우

```sql
WITH CommentTree
    (comment_id, bug_id, parent_id, author, comment, depth)
AS (
    SELECT *, 0 AS depth FROM Comments
    WHERE parent_id IS NULL
  UNION ALL
    SELECT c.*, ct.depth+1 AS depth FROM CommentTree ct
    JOIN Comments c ON (ct.comment_id = c.parent_id)
)
SELECT * FROM CommentTree WHERE bug_id = 1234;
```

```sql
SELECT * FROM Comments
START WITH comment_id = 9876
CONNECT BY PRIOR parent_id = comment_id;
```

## 해법: 대안 트리 모델 사용

계층적 데이터를 저장하는 데는 인접 목록 모델 외에도

경로 열거(Path Enumeration)
중첩 집합(Nested Sets)
클로저 테이블(Closure Table)

와 같은 몇 가지 대안이 있다.

처음에는 인접 목록보다 복잡해 보일 수 있지만, 인접 목록에서는 매우 어렵거나 비효율적이었던 트리조작을 쉽게 해준다.

**경로 열거(Path Enumeration)**

 인접 목록의 약점 중 하나는 트리에서 주어진 노드의 조상들을 얻는 데 비용이 많이 든다는 것.
Comments 테이블에 parent_id 칼럼 대신, 긴 VARCHAR 타입의 path 란 칼럼을 정의. 이 칼럼에 저장되는 문자열은 트리의 꼭대기부터 현재 행까지 내려오는 조상의 나열로, UNIX 경로와 비슷. 심지어 '/'를 구분자로 사용해도 된다.

```sql
CREATE TABLE Comments (
  comment_id   SERIAL PRIMARY KEY,
  path         VARCHAR(1000),
  bug_id       BIGINT UNSIGNED NOT NULL,
  author       BIGINT UNSIGNED NOT NULL,
  comment_date DATETIME NOT NULL,
  comment      TEXT NOT NULL,
  FOREIGN KEY (bug_id) REFERENCES Bugs(bug_id),
  FOREIGN KEY (author) REFERENCES Accounts(account_id)
);
```

만약 조상 찾는다면?
```sql
SELECT *
FROM Comments AS c
WHERE '1/4/6/7/' LIKE c.path || '%';
```

반대로, 후손을 찾는다면?

```sql
SELECT *
FROM Comments AS c
WHERE c.path LIKE '1/4/' || '%';
```

**중첩 집합**

중첩 집합은 각 노드가 자신의 부모를 저장하는 대신 자기 자손의 잡합에 대한 정보를 저장. 이 정보는 트리의 각 노드의 두 개의 수로 부호화(encode)해 나타낼 수 있는데, 여기서는 nsleft 와 nsright 로 부른다.

```sql
CREATE TABLE Comments (
  comment_id   SERIAL PRIMARY KEY,
  nsleft       INTEGER NOT NULL,
  nsright      INTEGER NOT NULL,
  bug_id       BIGINT UNSIGNED NOT NULL,
  author       BIGINT UNSIGNED NOT NULL,
  comment_date DATETIME NOT NULL,
  comment      TEXT NOT NULL,
  FOREIGN KEY (bug_id) REFERENCES Bugs (bug_id),
  FOREIGN KEY (author) REFERENCES Accounts(account_id)
);
```

## 클로저 테이블

```sql
CREATE TABLE Comments (
  comment_id   SERIAL PRIMARY KEY,
  bug_id       BIGINT UNSIGNED NOT NULL,
  author       BIGINT UNSIGNED NOT NULL,
  comment_date DATETIME NOT NULL,
  comment      TEXT NOT NULL,
  FOREIGN KEY (bug_id) REFERENCES Bugs(bug_id),
  FOREIGN KEY (author) REFERENCES Accounts(account_id)
);

CREATE TABLE TreePaths (
  ancestor    BIGINT UNSIGNED NOT NULL,
  descendant  BIGINT UNSIGNED NOT NULL,
  PRIMARY KEY(ancestor, descendant),
  FOREIGN KEY (ancestor) REFERENCES Comments(comment_id),
  FOREIGN KEY (descendant) REFERENCES Comments(comment_id)
);
```
